# Research · EVE Online Browser Fitting Assistant

Reviewed November 22, 2026.

## Stack and Versions

**Decision** · Start with React and React DOM 19.3.1, Vite 8.3.8, `@vitejs/plugin-react` 6.3.0, and TypeScript 7.0.2. Use Node.js 26.13.1 LTS for builds and CI and support Node.js 24.21.0 LTS locally. Use Playwright 1.65.1 for browser acceptance and `node:test` for unit and contract tests. Check stable `latest` tags, Node requirements, and peer dependencies before creating the lockfile. Match the major versions of `@types/react`, `@types/react-dom`, and `@types/node` to their packages. Use `npm ci` for reproducibility and type-check, build, and test dependency updates. [React](https://registry.npmjs.org/react/latest) · [React DOM](https://raw.githubusercontent.com/facebook/react/v19.3.1/packages/react-dom/package.json) · [Vite](https://registry.npmjs.org/vite/latest) · [Vite React plugin](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react/CHANGELOG.md) · [TypeScript](https://registry.npmjs.org/typescript/latest) · [Playwright](https://github.com/microsoft/playwright/releases/tag/v1.65.1) · [Node.js LTS](https://nodejs.org/en/blog/release/v26.13.1) · [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/)

**Rationale** · Vite and Playwright support the selected Node versions. Node runs maintenance TypeScript with erasable type annotations, and `tsc --noEmit` checks types separately. The registry and upstream sources confirmed the versions. A local npm query hit a DNS error at the time of research. Verify install, build, and compatibility when creating the lockfile. [Vite 8.3.8](https://registry.npmjs.org/vite/latest) · [TypeScript in Node](https://nodejs.org/download/release/v24.15.0/docs/api/typescript.html)

**Alternatives considered** · The stable and LTS versions provide a verifiable baseline. `openapi-typescript` 7.13.0 relies on the JavaScript compiler API that changed in TypeScript 7. A narrow OpenAPI importer and normalized contract for typed Fetch adapters are sufficient for the ESI operations and avoid maintaining a second compiler for generation. [Generator package](https://github.com/openapi-ts/openapi-typescript/blob/main/packages/openapi-typescript/package.json) · [TypeScript 7 compatibility](https://github.com/openapi-ts/openapi-typescript/issues/2841) · [TypeScript 7 release](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)

## Fitting Engine and Pyfa Reference

**Decision** · Use the browser entry point of `eve-fit-engine@0.2.28` behind a TypeScript adapter in a Web Worker and supply our own `FittingDataset`. This version held the npm `latest` tag at review time. Recheck the tag and required API before locking dependencies. Pin Pyfa v2.70.0, commit `e5483f8666ed2eda99c98985c59a29b07e3bb844`, and record exact dataset provenance and hash for the first corpus. Retain inputs, reference results, expected discrete values, and SC-001 tolerances. Verify module states, modifier order, constraints, capacitor cycles, and external effects. [Browser engine](https://developers.eveonline.com/docs/community/eve-fit-engine/) · [npm package](https://registry.npmjs.org/eve-fit-engine/latest) · [Pyfa release](https://github.com/pyfa-org/Pyfa/releases/tag/v2.70.0) · [Reference commit](https://github.com/pyfa-org/Pyfa/commit/e5483f8666ed2eda99c98985c59a29b07e3bb844) · [Pyfa calculation notes](https://github.com/pyfa-org/Pyfa/wiki/Fit-Calculation-Notes)

**Rationale** · The engine implements much of Dogma and has a Pyfa comparison harness. Independently verify results against FR-002–FR-006, including skill profiles, Abyssal, effects, and charts, and address confirmed coverage gaps. Desktop Pyfa uses wxPython and a derived SQLite database. Pin comparable source attributes and effects before comparison because the public SDE and the Pyfa release can differ. The engine uses GPL-3.0-or-later. Distribute the app under compatible terms with the required notices and access to corresponding source. [Engine repository and license](https://github.com/capsuleers-app/capsuleers.fitting-engine) · [Engine comparison harness](https://github.com/capsuleers-app/capsuleers.fitting-engine/blob/master/MAINTENANCE.md) · [Pyfa dependencies](https://raw.githubusercontent.com/pyfa-org/Pyfa/v2.70.0/pyproject.toml) · [Pyfa database preparation](https://github.com/pyfa-org/Pyfa/blob/master/db_update.py)

The engine API leaves separate work for XML and DNA codecs, a time series from the capacitor simulator, external sources with their own skills, and mining checks. Retain and flag unresolved entries before calling the engine because it may skip them. The Worker loads the necessary type groups from the pinned catalog before the synchronous calculation. The library's harness uses a different Pyfa commit, so SC-001 requires independent fixtures. [Engine API](https://github.com/capsuleers-app/capsuleers.fitting-engine/blob/master/src/index.ts) · [Types and effects](https://github.com/capsuleers-app/capsuleers.fitting-engine/blob/master/src/types.ts) · [Calculation entry point](https://github.com/capsuleers-app/capsuleers.fitting-engine/blob/master/src/engine.ts) · [Capacitor model](https://github.com/capsuleers-app/capsuleers.fitting-engine/blob/master/src/derived/capacitor.ts)

**Alternatives considered** · A custom TypeScript engine under the same Worker contract remains an option for confirmed limits or distribution constraints. Pyodide can run Python in a Worker, but porting the desktop stack requires dependency and I/O adaptation and startup checks on phones. Consider WASM for computation if optimized TypeScript still misses SC-002 in reproducible measurements. Evaluate WebGPU if profiling finds a suitable parallel computation. [Pyodide in a Worker](https://pyodide.org/en/stable/usage/webworker.html) · [Pyodide constraints](https://pyodide.org/en/stable/usage/wasm-constraints.html)

## PWA and Local Data

**Decision** · Use a manifest, service worker, and Cache Storage for the versioned shell, IndexedDB for the library and multiple catalog releases, and a Web Worker for calculation and the search index. Separate user records from replaceable catalog data. Activate the verified catalog with one IndexedDB transaction. Pin each calculation request to one data and rules combination until it finishes. Transfer the library by backup when installation uses separate storage. [Service Worker](https://w3c.github.io/ServiceWorker/) · [IndexedDB](https://w3c.github.io/IndexedDB/) · [Safari PWA storage](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/)

**Rationale** · After first download, users need a complete offline workflow and predictable release transitions. Request persistent storage where supported, base readiness on both the shell and catalog, and retain the active release on quota failures. A backup protects the library if the browser clears site data. [Storage Standard](https://storage.spec.whatwg.org/)

**Alternatives considered** · Synchronous Web Storage fits small optional preferences. The library needs transactions and catalog updates need concurrent versions. SQLite/WASM and OPFS add a separate format and infrastructure and should follow measurements showing the native storage is insufficient. Build the TypeScript service worker with a small controlled pipeline, an explicit lifecycle, and an exact resource list. [Web Storage](https://html.spec.whatwg.org/multipage/webstorage.html) · [File System Standard](https://fs.spec.whatwg.org/)

## SDE Import and Publication

**Decision** · Discover releases through official SDE HTTP, resolve `latest` once, and download aligned tables from the pinned `release` URLs. Check versions, schemas, references, and effect coverage. Use `_changes` and `_schemaChangelog` as report inputs and retain source data and verified artifacts for reproducibility. Check availability and SHA-256 of immutable files before switching the pointer. Store `buildNumber` for display because multiple releases can share it. [SDE documentation](https://developers.eveonline.com/docs/services/static-data/) · [SDE over HTTP](https://developers.eveonline.com/blog/the-sde-over-http-static-data-dynamically)

Verified snapshot `20261120T165826Z`, build `3724492`, has `release`, `buildNumber`, `releaseDate`, and `tables` keyed by name. Each table record includes `version`, `jsonl.url`, and `jsonl.recordSchemaUrl` for that release. Use `version` to detect table changes and computed SHA-256 for integrity. Verified tables include `types`, `groups`, `categories`, `marketGroups`, `metaGroups`, `typeDogma`, `dogmaAttributes`, `dogmaEffects`, `dogmaUnits`, `dynamicItemAttributes`, `dbuffCollections`, `typeBonus`, and `cloneGrades`. The source also includes `fighterAbilities`, `fighterAbilitiesByType`, `systemDbuffEmitters`, and `systemWideEffects`. Import the transitive references required by supported calculations. [Verified primary release manifest](https://sde.evetech.net/tranquility/20261120T165826Z/)

**Rationale** · SDE HTTP serves individual tables and retains two releases. Catalog data can ship independently of code. Include fitting adjustments and supported effect versions alongside the engine and in verification. SDE describes the in-game catalog, and Pyfa defines some rules and derived values. A verified snapshot pins the rows needed to build and rerun regression tests. [SDE documentation](https://developers.eveonline.com/docs/services/static-data/) · [Pyfa database builder](https://github.com/pyfa-org/Pyfa/blob/master/db_update.py)

**Alternatives considered** · Prefer official HTTP JSONL. The daily ZIP is a transitional source with a different schema, and CCP announced plans to retire the archives. Local import replays a stored HTTP snapshot. Add a verified archive adapter separately if needed. The SDE update process excludes the legacy ESI `/universe/` routes following CCP's migration. [CCP migration](https://developers.eveonline.com/blog/the-sde-over-http-static-data-dynamically)

## ESI Integration and Sign-In

**Decision** · Use EVE SSO Authorization Code with PKCE S256 for a public client and Fetch directly against ESI. Import OpenAPI 3.1 through npm with an explicit compatibility date, validate its schema, pin the used routes, and report changes. Start with `2026-11-19`, verified against live OpenAPI, and advance after review. Fetch skills, fits, and prices through ESI and obtain the catalog and Dogma through SDE. [EVE SSO](https://developers.eveonline.com/docs/services/sso/) · [ESI versioning](https://developers.eveonline.com/docs/services/esi/overview/) · [ESI schema for the selected date](https://esi.evetech.net/meta/openapi.json?compatibility_date=2026-11-19)

**Rationale** · Anonymous checks on November 21 at 17:40 UTC confirmed CORS for the token endpoint, discovery, JWKS, ESI preflight, and public prices. The token endpoint returned `204` on preflight and `401` with invalid parameters. Both carried `Access-Control-Allow-Origin: *`. Verify completed code exchange, token refresh, and fitting operations in a browser with a registered public app and two authorized test characters. The local editor and EFT and XML exchange remain available if direct sign-in fails. Integration acceptance requires a live check. [Sign-in and token validation](https://developers.eveonline.com/docs/services/sso/)

**Alternatives considered** · A confidential OAuth client requires a separate service that holds the secret. Consider that architectural change only if live testing confirms an EVE SSO incompatibility. ESI replaced legacy Swagger with OpenAPI. [ESI migration to OpenAPI](https://developers.eveonline.com/blog/goodbye-swagger-removing-the-last-remnants)
